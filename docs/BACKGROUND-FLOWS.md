# 当前活动与后台流程

Pocket 每日日程支持一项当前人工活动和多个并行后台流程。普通固定项目、计划的计时和暂停规则不变；机器运行、等待回去处理的时间不占用人工活动计时。

## 洗衣示例

在“后台流程”右侧点加号。默认提供洗衣服、洗涤 60 分钟、烘干 60 分钟，可修改名称、分钟数、增删阶段，再保存。

1. 点击“开始处理”，开始记录送衣服、装衣服的人工时间。
2. 启动洗衣机后点击“开始洗涤”。同一事务结束这一段人工计时并保存后台阶段和预计结束时刻，现在可以开始学习等其他活动。
3. 到点发送阶段通知，卡片显示“待处理”；不会自动认定洗涤已经实际完成。结束其他人工活动后点“去处理”，记录实际回去处理的时刻，并开始新的人工段。
4. 把衣物放入烘干机后点击“开始烘干”，再次让出人工计时器。
5. 回去取衣服时点“去处理”，收好后点“完成流程”。流程进入“已完成流程”，可从省略号查看阶段时间和编辑备注。

当前人工计时器仍可暂停、继续、写独立备注；通用结束键只结束人工段，之后可“继续处理”。一个后台流程不会阻止另一个流程等待运行。暂停的人工计时仍需先结束才能切换其他人工活动。

## 时间的含义

|数据|含义|
|---|---|
|投入|该流程各个人工会话的有效时间之和，扣除暂停，保留既有不超过 30 秒不入历史的规则|
|历时|首次开始处理至明确完成之间的墙上时间，包含机器等待及延迟处理；不累加进人工当日总时长|
|阶段开始|点击“开始某阶段”的实际时刻|
|预计结束|阶段开始加设置的分钟数，用于倒计时和通知|
|处理|用户点击“去处理”的实际时刻，可早于或晚于预计结束|

阶段时间是用户操作记录，应用不连接洗衣机，不测量机器的实际停机时刻。到点后保持待处理，不自动推进或完成；通知也不会自动开启人工计时。流程开始后阶段配置锁定，保留可核查的时间线；名称和整体备注仍可编辑。重新打开保留原流程历史，新的一次洗衣应新增流程。

## 实现与兼容

后台流程仍为原有 `records.type=task`，在 `properties.background_flow` 中保存经过校验的 JSON。没有新业务表，没有重命名 IndexedDB，不更改 Dexie v5 或 schemaVersion 1 备份。原电脑白板能接收相同任务及属性；阶段控制和时间线界面位于 Pocket。

`background-flow.ts` 定义阶段和进度；`flow-repository.ts` 在事务中关闭人工会话、推进阶段并写入操作日志；`flow-ui.ts` 展示卡片、阶段编辑和时间线。阶段最多 12 个，每段 1–10080 分钟。人工段仍为原 `sessions`，不把后台时间伪装成人工会话，也不重复建立计划。

TS 与 Python 对流程 JSON 使用相同的校验和合并规则。因果后继优先；并发快照优先保留推进更多的阶段，流程结束优先，避免旧设备的其他属性编辑退回已处理阶段。明确观察过完成后的重新打开仍可生效。离线并发人工计时延续既有策略：保留冲突会话，用户分别处理。

Drive 保持手动交换。各设备点“立即同步”后取得同一任务的阶段和人工会话；本功能不恢复自动双控。备份携带流程属性和会话，恢复按稳定 ID 幂等合并。

## 通知

已关联通知的设备联网提交阶段名称、分钟数、预计结束和处理状态等必要元数据，复用现有一年期设备凭证，不需要每次重新 Google 授权。计划正文、流程备注、人工计时历史和录音不进入通知服务。

每阶段使用“任务 ID + 流程 ID + 阶段 ID + 预计结束”作为去重键。处理阶段后撤销旧安排，开始下一阶段再安排新通知，完成/删除/归档后取消。离线新建阶段须联网并确认安排上传，才能在网页关闭时收到提醒。系统投递条件和限制见 [NOTIFICATIONS.md](NOTIFICATIONS.md)。

## 验证

数据测试覆盖洗衣三个人工段、两个后台阶段、多个流程并行、暂停锁定、短记录阈值、错误事务回滚、时钟回退、旧属性并发合并、手动 Drive、备份和 SQLite。浏览器场景覆盖完整处理、刷新、离线、320px 长标题及时间线。真实 workerd 定时集成测试验证两个阶段独立生成加密 Web Push，并解密核对提醒文本与去重标识。自动化不替代新阶段通知的手机实收确认。
